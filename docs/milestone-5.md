# Milestone 5: Scottie Scheffler Golf ingestion (implementation complete; acceptance open)

The bounded M5 slice stores one confirmed Scottie Scheffler PGA stroke-play tournament from Sportradar Golf trial REST data. It preserves tournament dates as dates, actual tee times as UTC instants, four provider round identities/statuses, Scottie's field entry, leaderboard totals, selected-round scorecard facts, and source clocks. The profile endpoint established Scottie's UUID during provider proof; routine ingestion uses that UUID and does not refetch his historical profile.

## Run

Export the existing `SPORTRADAR_API_KEY` privately (the CLI does not auto-load `.env`). Then:

```sh
python3 -m sports_briefing ingest scheffler
python3 -m sports_briefing inspect scheffler
python3 -m sports_briefing timeline
python3 -m sports_briefing timeline --show-results
python3 -m unittest discover -s tests -q
```

The CLI uses the current UTC calendar year and calls the PGA schedule. Discovery checks at most two current stroke-play tournaments, the three nearest upcoming within 60 days, then three most recent completed within 60 days. It fetches each summary until Scottie's UUID appears in `field`; a schedule listing or profile history alone never confirms participation. If none qualifies, ingestion fails clearly and the previous database state stays intact. This probe cap is not exhaustive season coverage. Tournament summary, leaderboard, and the selected round's tee times and scores complete one validated bundle. Requests are spaced to respect trial throughput. Cup, team, match and mixed formats are outside scope.

An authenticated September 23 upcoming-tournament summary returned HTTP 200 with no `field`, `rounds`, `status`, or `x-generated-date`. Such a discovery response is treated as unconfirmed and skipped. It is not evidence of withdrawal or non-participation. Every response accepted into persisted Scottie state still requires `x-generated-date`. Per-request logs and the CLI's `requests` versus `accepted_endpoints` fields distinguish probes from the accepted bundle.

## Tables and provenance

`golf_tournaments` stores provider tournament identity, PGA tour/season identity, date-only start/end, timezone, status, and stroke-play type. `golf_entries` stores Scottie's confirmed field identity, nullable leaderboard status/result, and nullable `result_finalized_observed_at`. `golf_player_rounds` stores round UUID/number/status and nullable Scottie-specific tee time/score/thru/scorecard timestamps. `golf_sources` keeps one bounded latest raw response per endpoint scope, parsed and raw `x-generated-date`, ETag, Last-Modified, semantic hash, accepted time, and last fetch time. `golf_fetches` retains the last 20 successful batch outcomes; it does not store an event history. Initializing an existing database adds the nullable entry column without backfilling past results; read-only inspection of a pre-migration database treats it as null.

All endpoint revisions are checked before any domain write within one SQLite transaction. Stable provider keys upsert normalized rows. Identical Scottie-specific semantics do not change domain `last_changed_at` or source `accepted_at`; a later generation header with identical semantics advances only the source high-water clock and fetch diagnostics. Older generations and equal-generation conflicting content fail without partial replacement. Newer generations with changed semantics update state. This is a conservative provisional policy: actual monotonic behavior across a changed Golf response is not yet observed. ETag and Last-Modified never order sports state. The schedule revision is scoped to the selected tournament, so a different confirmed tournament does not conflict with an unchanged full schedule generation.

Each source hash covers only that endpoint's normalized facts. A scorecard-only update cannot change the leaderboard hash, and a summary date or round-list change is checked against the summary's own generation clock. If a newer complete summary/leaderboard omits a previously accepted round identity, ingestion rejects the batch atomically. The provider's round-retirement semantics have not been observed, so the stored last-known state remains available with an explicit failure instead of silently leaving an orphaned tee-time row after a successful refresh.

## Home timeline

Golf emits a confirmed upcoming round with an actual player tee time, tournament and round both `scheduled`, and no observed nonzero round score, positive strokes/holes, or explicit exception status. A tee time within 24 hours produces `IMMINENT`; within seven days produces `ROUTINE`. One nearest round candidate per Scottie is selected. An accepted, previously known nonterminal-to-final transition can produce `RECENT_RESULT` for 36 hours after *Sports Briefing first observed finalization*. The shared ranker and tiers are unchanged; Golf `result` remains null. `LIVE` and `MEANINGFUL_CHANGE` remain disabled for Golf. No status is inferred from missing player/tee-time data.

The timeline `--as-of` switch evaluates current persisted state; it is not historical replay. The API `GET /timeline` uses the same candidate adapter and remains spoiler-safe by default. Hidden Golf results use a neutral summary and no structured `result` object; position, tie, score, strokes, winner, and exception outcome do not appear. `--show-results` uses supported position, tie, score, and strokes in the summary while leaving the football-shaped structured `result` null.

### Product-observed finalization clock

Sportradar provides terminal result state but no proven tournament-completion timestamp. `result_finalized_observed_at` is the UTC time when **Sports Briefing first accepts a known Scottie tournament/player transition into a complete final result**. It is neither provider completion time nor provider generation time. The field is set atomically with the accepted update and never refreshed by a rerun, new ETag/fetch time, terminal correction, or temporary reopening. An unknown tournament imported already closed, including the historical completed tournament used for authenticated validation, retains null. A previously stored closed result that later gains missing fields also retains null.

The transition requires a previously stored confirmed Scottie entry with no explicit exception status and tournament status `scheduled` or `inprogress`; the new stroke-play tournament must be `closed`, have at least one round and all declared rounds `closed`, Scottie must still have no explicit exception status, a positive position/strokes and integer total score, and every recorded Scottie round must have 18 holes plus integer score and positive strokes. It deliberately excludes cut/WD and contradictory partial results. The course-local observation date must fall on the tournament's stated end date or the next local day. This date bound is only a historical-import safeguard; the end date is never used as the observation or completion timestamp. A valid late final result outside that window stays stored but gets no recent-home clock. Unknown course timezone or naive observation timestamp causes the transition batch to fail rather than guess.

A currently complete stored result enters `RECENT_RESULT` only when the sticky product-observation time is between now and 36 hours ago, inclusive. The candidate's event/ranking time is that observation, and its reason remains the existing deterministic `recent_result`. A later reopening keeps the timestamp but suppresses the candidate while state is nonterminal. The source reference points to the accepted leaderboard revision. This means “a result Sports Briefing observed become final recently,” not “Sportradar says the tournament finished at this exact time.”

The transition is verified with synthetic successive snapshots because no actual Scottie finalization occurred during this implementation pass. Tests cover historical bootstrap exclusion, accepted transition, sticky rerun/correction/restart, rejected revisions, atomic rollback, late observation exclusion, the inclusive 36-hour boundary, hidden CLI/HTTP output, and unchanged global ranking order. This pass has 37 focused Golf and 118 complete offline tests passing. No new authenticated polling was needed; the already authenticated completed tournament remains a first-import historical result with no observed-finalization timestamp.

The local existing database was inspected read-only before migration, then initialized twice. It acquired exactly one nullable observation column; every preexisting column value and row count across the 12 existing tables remained identical. The stored completed-tournament entry still has a null observation time and yields no recent-result candidate. In a separate synthetic database, a known nonterminal state became final at a synthetic observation time; an identical rerun gave zero inserts, zero updates, six unchanged domain rows, and five unchanged sources while preserving that timestamp. A restarted CLI produced deterministic hidden output. Loopback HTTP returned 200 for both spoiler states: hidden output was neutral; revealed output used the stored position, score and strokes, with no shared structured result object. These checks verify the new product rule, not a live provider transition.
